Master roadmap **and execution log** for Gabriel's evolution into the v2.0 project-agnostic OSINT
data-fusion environment. This file is the single place an executing agent reads to know *what to do

## How to use this file (execution protocol)

An agent executing this roadmap **must** follow this loop:

1. **Work top to bottom, one item at a time.** Do the lowest unchecked `[ ]` item in the current phase.
2. **Read the 📎 reference first.** Each item links to the doc that holds the *how* and *why*. Do not
   invent behaviour that contradicts an ADR or `CONSTRAINTS.md`.
3. **Keep the build green.** `npm run verify` must pass at every commit. One item ≈ one revertible commit.
4. **Check the box and annotate.** When an item is done, set it to `[x]` and, if anything is
   non-obvious, add a `> note:` line under it (what you chose, what you skipped, what to revisit).
5. **Stop at every 🔒 Phase Gate. Do not self-certify.** A gate is crossed only after a **separate
   validation agent** (fresh context, not the agent that did the work) verifies the ✅ success
   criteria against the real repo + git diff, runs `npm run verify`, and records a verdict in the
   **Validation Log**. Proceed only on `PASS`. On `FAIL`, address the feedback and re-request validation.
6. **Log the load-bearing stuff, not everything.** Use the **Execution Ledger** at the bottom for:
   points intentionally *not* done, things to validate later, and anything that could bite later.
   Skip blow-by-blow detail — record only what a future reader would need to avoid a mistake.

**Status markers:** `[ ]` todo · `[x]` done · `[~]` partial/in-progress · `[!]` blocked
**Icons:** 📎 technical reference · ✅ success criteria · 🔒 phase gate (separate-agent validation)

## North star (Gabriel v2.0, FNF deliverable)

An open-source, **project-agnostic** data-fusion environment holding *entities, sources, ADMIRALTY
ratings, and geometries in a single auditable structure*, that any team can point at an adjacent
accountability domain. v2.0 grows these producer modules on top of today's ORBAT editor: Telegram
graph, corporate/sanctions graph (ETL), maritime (AIS/ADS-B), GEOINT (satellite change-detection) —
each behind an abstract capability interface, run as a local sidecar first. The deployed read-only
public map for consumers is a permanent, separate requirement, unaffected by any of this.

**Sequencing principle:** the foundation (Streams 1 & 2) comes *before* new modules. We do not build
the second module on the type-first, string-provenance foundation.

  - 🔒 Gate E1 — separate agent runs the round-trip test on real fixtures + confirms the deletions.
  > note (in progress, landing as a sequence of commits — types → persistence/migration → store → UI merge → deletions):
  > **E1.1 (this commit) — `Entity` gains `CorporateProfile`, decided "D1-loose".** `Profile = UnitProfile | CorporateProfile` is a real 2-member union now, discriminated by `kind: "unit" | "corporate"`. But `Entity` itself is deliberately **not** a strict discriminated union — every profile field (`type`, `echelon`, `affiliation`, `domain`, `natoSymbolCode`, `militaryUnitId`, `osmRelationId`) stays optional regardless of `kind`, so the ~15 direct `entity.echelon`-style reads already shipped across `modules/orbat` in Stream 1 keep compiling with zero forced narrowing. A strict union would have required touching every one of those call sites just to add a second profile — a much larger, riskier diff for a mechanical-in-spirit migration, and arguably not what ADR 0004's "flat, not nested" reasoning (protecting the GeoPackage column decode / store shallow-merge / inspector reads) was actually asking for once a second profile made `keyof (A|B)` bite. `asUnitProfile`/`asCorporateProfile` guard helpers exist in `core/entity/entity.ts` for the few places that need strict, kind-safe access (persistence encode/decode, the Corporate `type` select requiring the closed `OrganisationType` enum). This is a documented reinterpretation of ADR 0004's "discriminated union" language, not an oversight — flagged here since it's exactly the kind of "non-obvious decision" this file exists to record.
  > A real gotcha hit while implementing: naively writing `Entity = EntityCore & Partial<Omit<UnitProfile,"kind">> & Partial<Omit<CorporateProfile,"kind">>` does **not** produce `type?: string`; TypeScript intersects same-named properties across an intersection type, narrowing `type` to `OrganisationType` only (since it's a subtype of `string`) and rejecting free-form unit type keys like `"infantry"`. Fixed by flattening `Entity` explicitly with `type?: string` rather than relying on automatic intersection.
  > Also fixed a latent circular-import risk: `types/organisation.types.ts` imported `PositionMode` from `types/domain.types.ts`, which now imports `Entity` from `core/entity/entity.ts` — and `entity.ts` needs `OrganisationType` from `organisation.types.ts` for `CorporateProfile`. Repointed `organisation.types.ts` to import `PositionMode` directly from `core/entity/entity.ts` (its real home; `domain.types.ts` only re-exports it) to break the cycle before it could form.
  > **E1.2 — `units` table gains a real persisted `kind` column.** `kind` stops being a read-time-injected fiction (Stream 1's B1 design, valid only while `Profile` had one member) and becomes an actual `TEXT NOT NULL DEFAULT 'unit'` column, `optional`/`fallbackSql`'d exactly like `analyzed_at`/`position_mode`/`is_exact_position` before it — every row predating this column was a unit (the `organisations` table is where non-unit rows used to live), so the fallback is correct by construction. `type` and its shared column now branch decode/encode on `kind` (`decodeOrganisationType` for corporate rows, free-form string passthrough for units) — `kind`'s descriptor is positioned before `type`'s in `unitColumns` since `DecodeContext.decoded` only exposes earlier-in-array props. `osmRelationId` needed no branching: both profiles declare it identically (`number | null`). Added 3 tests to `units.table.test.ts`: a corporate row round-trips with its enum-validated `type` distinct from a unit's free-form `type`; an invalid persisted corporate `type` value defaults to `"other"`; a table missing the `kind` column entirely (simulated via `ALTER TABLE units DROP COLUMN kind`, mirroring `geopackage.service.test.ts`'s existing pre-migration-column technique) defaults every row to `kind: "unit"`. `npm run verify` (198 tests, +3) and `storybook build` both green.
  > **E1.3–E1.6 (one combined commit) — migration-on-read, store collapse, and UI merge.** TypeScript's static coupling forced these together: the moment `GeoPackageLoadResult`/`ProjectState` shapes change, every consumer (persistence, store, and every UI file reading `s.organisations`/`selectedOrganisationId`) breaks in the same compilation unit — there is no way to land a genuinely-green intermediate commit between "store still has `organisations`" and "store doesn't", so splitting into 4 separate commits here would have meant fake-atomizing an inherently-coupled change (same reasoning as Phase C's C1–C3). Flagging openly for Gate E1 rather than hiding it.
  > **Migration**: `organisations.table.ts` is now read-only — `createOrganisationsTable`/`writeOrganisations` are deleted; `migrateLegacyOrganisations(geoPackage): Entity[]` maps legacy rows to `kind: "corporate"`, pinned to `layerId: INDUSTRY_LAYER_ID` (Organisation never had its own `layerId`). `load.ts` concatenates `readEntities()` (now real `kind`-tagged rows) with `migrateLegacyOrganisations()` into one `entities` array; `GeoPackageLoadResult`/`ApplyGeoPackageResultState` drop `organisations`/`selectedOrganisationId` entirely. `save.ts` never creates or writes the `organisations` table again — an old file's table is left in place as harmless orphaned schema debris rather than dropped (no `DROP TABLE`), to avoid an untested destructive step for a cosmetic win.
