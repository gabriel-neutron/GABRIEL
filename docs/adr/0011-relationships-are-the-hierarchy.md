# Relationships are the hierarchy, and the retained `parentId` is a derivation rather than a second copy

Decided 2026-07-31, in the slice that ships the first write to `public/project.gpkg`. The
migration code lands here; running it against the real file is a separate, deliberate act.

The `relationships` table becomes the **only** record of who sits under whom. `Entity.parentId` is kept, and is **derived** — recomputed from the active hierarchy-bearing edges on every load and on every edge mutation, by one pure pair of functions (`activeParentMap`, then `withDerivedParents`) and by nothing else. A one-time migration, gated on the **absence** of the `relationships` table and not on its row count, mints one edge per parented entity from the legacy columns: **1012 edges for the 1012 parented entities among 1027** — 999 `subordinate_to` from `units.parent_id` and 13 `corporate_parent` from the legacy `organisations` table, leaving 15 roots. Every minted id is the string `hier:` followed by the child id, which is unambiguous because no id in the file contains a colon.

ADR [0010](0010-first-class-relationships.md) already ruled that Hierarchy is one derived view over typed edges. This ADR records the four decisions that ruling only becomes concrete enough to argue about when it meets a real 4,984,832-byte file with one irreplaceable copy of the analyst's work in it.

## Why

**The retained `parent_id` column is not a backup, and reading it as one is the single most likely misreading of this change.** After the migration the column is still populated — 999 unit rows and 13 organisation rows, rewritten rather than nulled — and a future reader who sees that will relax. They should not. What the column holds after the first save is the *derivation*, not the original data. The two are written by the same save, in the same instant, from the same source: if `relationships` is ever empty, every derived parent goes null and the column is nulled with it. Primary and "backup" fail together and are perfectly correlated, which is the one property a backup may not have. The real backup is the repository's git history, pinned at **`5b0d2ed`** and pushed to `origin/telegram-osint-sidecar` before the migration first runs. That is the revert point, and it is the only one.

**Corrected 2026-08-04.** This paragraph originally said *the private repository's* git history. `github.com/gabriel-neutron/GABRIEL` is **public** — verified against the API, not assumed — so the sentence was false on the fact its whole argument rests on. The argument survives the correction: git history is still the only uncorrelated copy, and `5b0d2ed`'s blob is still byte-identical to the file on disk (md5 `7d0b0e59…`, 4,984,832 bytes, re-verified the same day). What changes is everything the word *private* was silently carrying — the working file, its 1,027 entities and the named natural persons inside it are world-readable, and have been since the repository was created on 2026-05-05. The owner has ruled that code and data are both public, so this is now the intended state rather than a leak; it is recorded here because a reader who meets the word "private" in a backup argument will draw conclusions about confidentiality that this project does not support. `docs/GABRIEL_V2_PRD.md`'s requirement 89 and its baton-pass rule, which required a private repository for a different reason, are superseded by that ruling. This restates ADR 0010's consequence in the slice that makes it operational, because that is the slice in which believing otherwise costs the data.

**The migration has no `kind` heuristic because it does not need one: the two populations live in physically distinct tables.** The `units` table has **no `kind` column** — all 1010 rows decode to `"unit"` by fallback — and every `corporate` entity in the file comes from the legacy `organisations` table alone. So the classification is not a judgement made at runtime about what an entity looks like; it is a fact about which table a row was read from. That is what makes "one rule for the 999 unit links, one hand-written id-keyed table for the 13 corporate ones" structurally safe rather than a heuristic dressed up as a rule. The 13 are enumerated as literal child ids with literal parent ids, so a wrong classification is a line in a diff that a reviewer can see, not an inference nobody can reconstruct after the fact. The table is keyed on **ids, never on labels**: the corporate parent's real name in the file is `Rostec State Corporation`, and every document that abbreviates it to "Rostec" is a document that cannot be used to key a migration.

**A contested child derives `null` because the conflict is a finding, and a control that resolves it silently destroys the finding it exists to hold open** (Q40). A child carrying two competing active hierarchy-bearing edges is **absent** from the derived parent map. It is not mapped to `null` by a tie-break rule, and no winner is picked — not the earliest, not the lowest id, not the first read. Any such rule would produce a tree that renders cleanly and is wrong in a way nothing can detect afterwards, because the losing edge leaves no trace in the result. Dual subordination is one of the things an ORBAT analyst is looking *for*; the right response is to show nothing and say so. The competing edge ids are returned alongside the map, at the point the conflict is decided, so the caller mints the integrity event without running a second validation pass to rediscover what the derivation already knew. The same predicate, `isHierarchyBearing`, backs both the derivation and the `multiple-active-hierarchy` violation, so the control and the derivation cannot come to different conclusions about the same pair of edges.

**The two percentages are frozen literals because the obvious parser publishes a defamatory falsehood on its first run** (T12). The source prose lives in `organisations.notes`. The Kalashnikov note contains **two** percentages, and the first one, `95%`, is a *market* share — "Produces 95% of Russian small arms". Any regex of the obvious shape captures 95 first and mints "Rostec holds 95% of Kalashnikov Concern", which is false, defamatory, and destined for a CC-BY dataset. The KAMAZ note reads `c.49.9%`, so the precision qualifier would need a second ad-hoc strip; two ad-hoc rules for two rows is the signal that there should be no rule at all. And a parser is not a one-time risk but a permanent liability: it re-runs on every migration against notes an analyst edits later, in prose written by someone who does not know their sentences are being read by a machine. So `49.9` and `25` are written into the migration table by hand with the source sentence beside them, `49.9` never rounded to `50` (it sits deliberately below the control threshold), `25` never inflated to encode the "+1 share" (fabricating a value to carry a legal effect invents unsourced data in a published field). **Omitting the percentages would be worse than either**: `corporate_parent`'s published definition says that where no percentage is recorded, no ownership share or controlling interest has been established, so a bare edge on Kalashnikov would read as *more* control than 25%, against a source that explicitly denies it.

**The mirror case is the one with the opposite stake, and it is why this is a rule and not a preference.** Rosoboronexport's note says it is the "sole state intermediary for all military export contracts" — a sentence that reads like an invitation to mint an `acts_for` edge. Minting it automatically would launder an analytical judgement into a documentary record, which is exactly the confusion the record/assessment tier split exists to prevent (ADR 0010), and no machine-minted edge can carry the two-person `ExportOverride` that an assessment-tier edge needs before it may be published (ADR [0009](0009-machine-never-confirms.md): the machine never confirms). So the set of types this migration can emit is a two-element literal, and `acts_for` is unreachable from the module by any path, including configuration.

## Considered options

- **Keep `parent_id` as an authoritative second copy and reconcile the two on load.** Rejected: two answers to one question on the exact seam this slice exists to close. Reconciliation needs a tie-break, the tie-break is a heuristic, and the first divergence would be discovered by an analyst noticing a unit in the wrong place rather than by any check.
- **Null the `parent_id` column after migrating, so nobody can mistake it for a record.** Rejected: `buildOrbat` and its six production callers read that field, and nulling it would force the Slice 3 consumer rewrite into the same irreversible commit as the migration (T14). Keeping the column *derived* is what lets those consumers change by zero lines.
- **Treat an empty `relationships` table as "not yet migrated" and re-mint.** Rejected, and this is the sharpest gate in the slice (T11). Deterministic `hier:` ids prevent duplication, not **resurrection**: after the first save, `parent_id` holds the derivation, so a second migration run from that column would faithfully recreate an edge the analyst had deliberately deleted, and with it the dual subordination they had resolved. That failure is invisible and effectively un-undoable. The gate is therefore on the **absence of the table**, never on a row count.
- **Infer `corporate` from entity shape and mint `corporate_parent` by rule.** Rejected: the shape does not carry the information — the `units` table has no `kind` column — so the "rule" would be a proxy for the table the row came from, expressed less legibly and checked nowhere.
- **Pick a winner for contested children — earliest start date, or lowest edge id.** Rejected: it renders a clean tree over a real conflict and leaves no evidence that a choice was made.
- **Map contested children to `null` in the parent map rather than omitting them.** Rejected as a smaller version of the same mistake: `null` is what an unparented root looks like, so the conflict would be indistinguishable from a legitimate root at every later read. Absence from the map is a distinct state, and the caller decides what to do with it.
- **Parse the percentages out of `notes` at migration time.** Rejected on the 95% market share alone; rejected a second time because a parser re-runs over analyst prose forever.
- **Ship the 13 corporate edges without percentages and add them later by hand.** Rejected: the published definition makes a missing percentage a positive statement that no share has been established, so "later" is a period during which the dataset asserts something false about Kalashnikov.
- **Build a preview UI for the migration so the analyst can inspect it before it runs.** Rejected (and already forbidden by the Slice 0/1 decisions): the two hashes taken in the rehearsal — the `entityId -> parentId` map and the rendered position map — compare bit for bit, which a screenshot cannot, and a screenshot cannot show an entity that is absent.

## Consequences

- **`parentId` survives as a derived field, so the tree code does not move.** `buildOrbat` (`src/core/entity/hierarchy.ts`) and its six production callers change by **zero lines**. A `hierarchyIndex` and an `Orbat.parentOf` that take those consumers off `parentId` and onto edges are **Slice 3, and are deliberately not built here** (T14): a migration and a consumer rewrite in the same irreversible commit is not a commit anyone can review. `activeParentMap` fills the field; `buildOrbat` reads the field. Different storeys.
- **The three remaining write sites to the derived field are ported in this slice** (T16), because a write to a derived field is either a crash or, worse, a change that survives until the next save and then evaporates: `mergeEntities` (`src/core/identity/merge.ts`), the inspector's parent change (`src/modules/orbat/hooks/useEntityInspector.ts`, whose coupling to `positionMode: "none"` on clearing a parent must survive the port), and entity creation under a parent (`src/shell/MainLayout.tsx`). After the port, every hierarchy write is an edge operation.
- **A count of edges is not evidence that the migration worked.** **741** of the 1010 units take their map position from the parent chain (599 with `position_mode` `"none"` plus 142 with `"parent"`), so the derived parent map can be subtly wrong while the edge count reads a perfect 1012 and 741 units silently move or vanish. The rehearsal fingerprints the **rendered** position map for this reason, and it is the only assertion that catches that failure.
- **Contested children are visible but unresolved, and there is no UI to resolve them.** They land in `integrity_events` with both competing edge ids, and a contested entity derives no parent until a human deletes or dates one of the edges. That is the intended state, not a gap to close quickly.

  **Corrected 2026-08-04.** *Visible* was false, and it was false for the same reason this ADR gives four paragraphs above for rejecting `null`: the retained `parentId` field is one nullable string, so a contested child came back from `withDerivedParents` carrying exactly what a legitimate root carries. Three independent review lenses — architecture, OSINT-analyst, publication — found the same defect without seeing each other's answers. `buildOrbat().roots()` returned a contested child as a top-level formation, so true root, orphan and contest rendered identically; `computeAllEntityPositions` dropped it at the `parentId != null` filter and **its entire subtree with it**, which for the 741 units that take their position from the parent chain makes "record a contest" and "the unit disappears" the same operation; and `HierarchyPanel` filed it under an empty state reading `No units without a parent`, a sentence that is false for an entity with two. This ADR ruled that mapping a contest to `null` "would be indistinguishable from a legitimate root at every later read" and then left the field doing precisely that. Publishing a contested child as a root is a *stronger* false claim than picking a winner would have been: "this unit answers to no one" is an affirmative ORBAT assertion, and a reader cannot detect that it is wrong.

  **Slice 3 makes the sentence true.** `hierarchyIndex` returns a `ParentLink` — `root`, `parent`, `contested`, `unresolvable` or `unknown` — with the competing edges attached; `Orbat.parentOf` exposes it to the six consumers; `HierarchyPanel` badges a contest and no longer claims the entity has no parent; `computeAllEntityPositions` returns the contested-and-unplaced ids instead of swallowing them, and still invents no position, because a midpoint between two competing parents is fabricated data. **No UI to resolve a contest was added, and none should be**: showing that a contest exists is not resolving it, and the ruling above stands.
- **A cross-kind hierarchy edge is a legitimate record that must not derive a parent.** The existing entity validation throws when a `parentId` does not resolve within the same kind, so a `unit`-to-`corporate` hierarchy edge would derive a value that makes the *next* load fail. The pair is filtered where the kinds are known, by omission from the map, and a `cross-kind-parent` event is recorded. It does not throw: throwing would make a legitimate record unopenable.
- **A migration failure is not file corruption and must not be reported as one** (T13). The count assertion — parented entities equal minted plus already-present — throws a message beginning `Hierarchy migration`, and the load path passes that prefix through unwrapped. Throwing is safe here only because nothing has been written: the load path never exports the GeoPackage, the throw precedes `setProject`, and the save guard therefore refuses every save. The app opens empty **and inert**, not empty and armed.
- **The migration's own record is a row, not a log line.** One `hierarchy-migrated` integrity event, whose `summary` is a sentence worth publishing and whose `detail` carries the two source sentences verbatim, so the derivation of `49.9` and `25` is auditable inside the file rather than only in a commit message.
- **`EDGE_VOCABULARY_VERSION` stays `1.0.0`.** No vocabulary entry moved, so nothing here is an amendment under ADR 0010; the only change under `src/core/relationship/` is the single hierarchy predicate and its consumers.
- **This lands in the same slice as the migration, not after it.** An ADR that explains an irreversible write is worth least on the day the write is reviewed and most on the morning someone asks why the column is still full.
